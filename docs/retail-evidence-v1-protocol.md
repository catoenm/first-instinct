# Retail evidence, scope and prerequisites: bounded local collection

Use the qualified pinned retail tools with authored synthetic accounts. Preserve
all earlier studies and upstream code. Do not load official tasks or the upstream
database, query models, rent hardware or consume the reserved telecom examples.
This stage collects execution receipts only; question admission and any learning
comparison require later qualification.

## Three task contracts over two mechanisms

Start from the earlier synthetic customer, two orders and three gift cards. Before
the current decision, execute and retain three real public reads: email lookup,
user details, and target-order details. These are cached observations at epoch 0.
Apply the declared background transition, then begin the actor's decision at epoch
1. The current world is static after that point. Cache responses must be identical
within each task contract and must never be rewritten to match the new world.

The public task says the cache may be stale, states the finite uniform prior, gives
the requested address or payment goal, and confirms the simulated action. Hidden
configuration names, background receipts and verifier state stay private.
Identifiers must come from the actual cached public reads. Background changes are
explicit authored scenario transitions, not a claim that tau2 models autonomous
shipping or external banking activity.

**Address scope** has two goals: change only the target order's shipping address,
or change only the customer's default address. The other address and unrelated
orders/account fields must remain unchanged from epoch 1. Enumerate all eight
current configurations: profile address already desired/not, target address
already desired/not, and target order pending/processed. These settings are
independent and equiprobable. Address changes during the background transition use
the actual public modification tools while the order is pending; the subsequent
processed status is an authored external-fulfillment transition.

**Payment prerequisites** has one goal: move the target's existing 20-unit charge
from the old gift card to the new one exactly once, preserving the total charge,
items, addresses and status. Use four equally likely current conditions: pending
with sufficient new-card funds; pending after an external 40-unit debit leaves
insufficient funds; processed with sufficient funds; and already migrated. The
completed condition is produced by an actual background payment-migration call.
The external debit and fulfillment are authored state transitions, recorded
separately from tool calls. Some goals are unreachable using the offered menu;
stopping can then be preferable to another costly failure.

## Alternative execution and labels

Address menus contain: stop; write the order address; write the profile address;
inspect the goal's current object and update only if needed and permitted; repeat
that inspection before following the same procedure; and attempt the order write
before inspecting and completing the actual goal. The last branch can recover
from a refused write yet damage unrelated state when that same write succeeds.

Payment menus contain: stop; attempt migration; cancel the target; inspect current
user/order details and migrate only when prerequisites hold; repeat the order
inspection before the same procedure; and attempt migration before inspecting and
following that procedure. Do not infer success from a normal tool return. The
known cancellation/refund issue must receive its actual failed-goal verdict if
encountered; no monetary gain from it contributes positive reward.

Every procedure uses only cached public identifiers and its own actual public
responses. Recognize only the exact documented ValueError messages for a
non-pending target, insufficient gift-card balance, or an already-modified payment
history. Require complete state preservation after each expected error. Every
other exception stops collection and remains an infrastructure failure.

Execute six alternatives for each of the 20 goal/configuration pairs, each in a
fresh world and independently replayed once: **240 world executions maximum**.
Limit each world to 12 public calls (including cache, background and private
verification reads), 30 seconds, and the collection to 2,880 calls. Block outgoing
sockets and upstream task/database reads. Preserve partial journals; do not retry
unexpected failures automatically.

Record immediate success after the first attempted actor command, and success
after the entire declared continuation. Compare goals with the complete state at
epoch 1, so already-paid/background events are not actor actions or free evidence.
Use independent address-scope and signed-ledger/wallet predicates, exact unrelated
state preservation, and private final public reads. Require exact replay of states,
responses, expected errors and costs. An order's processed status is a prerequisite,
not permission to rewrite the user's requested goal when it is unreachable.

## Accounting, grouping and checks

Value verified goal completion at 20 simulated units. Cross read fees 0.10, 2 and
10 with non-read attempt fees 0.25 and 6. Charge each future actor attempt, including
errors and redundant reads. Cache, background and verifier calls are counted as
execution work but excluded from future actor utility. Monetary transfers never
become rewards themselves. Average compatible worlds before choosing an action.

Keep every address-scope and payment variant in one **retail training-candidate
group**, including the earlier ledger fixtures. Do not create local train/test
splits among these related worlds. Audit complete initial-state and full-trajectory
overlaps within the cohort and against the reserved telecom evidence before any
question admission; shared worlds require connected whole-family ownership.
Count physical states separately from 20 goal/configuration slots and 240
executions. Costs and replay copies are not new tasks.

Require faithful cached histories, visible-information-respecting continuations,
fractional outcome groups, already-completed stop successes, charged expected
errors, redundant-read cost with unchanged terminal state, and cost-dependent
best actions. The address/profile and payment verifiers must reject wrong scope,
wrong net charge, excess refunds and unrelated mutations even if calls return
normally. Keep unexpected semantic failures visible and quarantine affected
structures rather than weakening predicates or dropping difficult configurations.
