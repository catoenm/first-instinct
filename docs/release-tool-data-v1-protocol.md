# Prospective first release-data stage: tool behavior from existing sources

This stage admits public behavior examples for a production decision model.
It does not execute source tools, infer verified outcomes, call a model, rent
hardware or train. Use new modules so all earlier experiment freezes remain exact.
Freeze this protocol, converter/test code, prior source receipts and source hashes
before producing a new candidate corpus. Preserve rejected attempts.

Start with only the three already-cached TOUCAN shards at revision
0df3cf37f2abefb380370cfb02eabea2a35ae782: Kimi-K2 shard 0, OSS shard 0 and Qwen3
shard 0. Their hashes and declared licenses are in results/toucan-audit-v2.
Recheck exact bytes against those receipts. Ceiling: 35,227 source trajectories,
one candidate first-tool question per trajectory, no download of extra shards.
Existing structural eligibility is not automatic admission.

An initial accepted example must contain exactly one first assistant tool call,
with an unambiguous declared function, public preceding user request and 2–36
distinct offered functions. Handle parallel first calls or clarification history
only in separately qualified extensions; initially reject them explicitly. Use
only evidence that existed before the chosen call. Assistant reasoning, future
tool responses, reference arguments, quality scores, source identifiers and
outcome metadata never enter the model prompt.

Present the actual function names, descriptions and parameter schemas as the
answer definitions. Validate arguments as a structural source check, including
schema/type/required-field constraints, without presenting the demonstrated
arguments as an answer hint. Reject unsupported schemas or unresolved references;
never fetch a remote schema or run source-provided code. Record every exclusion.

The target is explicitly observed first-tool imitation. It does not assert that
the choice was optimal, that arguments were generated by our model, or that the
task succeeded. Dataset judge scores remain provenance, never success labels or
calibration targets. Do not invent a negative none/clarify answer from the lack of
such examples; add those skills from separately qualified source annotations or
executable contracts.

Before labels are used for selection, assign servers to candidate usage with a
fixed hash of seed 20260921 and server identifier, using 80/10/10 train/development/
transfer buckets. Keep only within-role compositions; reject rows whose servers
span roles or whose server attribution is absent. This is a proposed ownership
construction to audit, not proof that the resulting splits are independent.

Join exact normalized requests across teacher subsets and exact normalized tool
schemas across server aliases. Preserve all contributing source row identities.
If those joins connect usage groups, remove the entire affected training or
development server group rather than moving any reserved group into learning.
Iterate to a stable ownership graph and report the attrition. Same-input conflicting
teacher choices remain an explicit rejected ambiguity group; do not majority-vote
them into certain ground truth or claim all observed choices are independently
verified correct. Exact agreement duplicates collapse with full lineage.

Audit overlap with earlier project development/test corpora and source-role records.
Do not reuse old test examples as new training simply because the producer changed.
Preserve protected application datasets in private output and the corrected
telecom evaluation-only usage manifest. If useful grouped training and evaluation
coverage does not survive, stop admission with a report. Do not relax ownership or
create random row holdouts; a separate source-held-out evaluation is the fallback.

Render the existing constrained-choice format using the pinned Qwen3.5-9B
tokenizer. Measure complete lengths, reject over 4,096 tokens without truncation,
and report the subset fitting the existing 1,536-token demo limit. Shuffle
option order deterministically independent of target before hashing/tokenizing.
Deduplicate exact visible and token inputs, retaining source lineage and rejecting
any cross-role collision. Context extension remains a separate model/runtime gate.

Export a private candidate corpus and a digest-bound usage manifest. Publish only
generic code, permitted aggregate statistics, source attribution and hashes at
this stage. Count source trajectories, eligible trajectories, unique requests,
tool schemas, server groups, token inputs, admitted questions and rejected groups
separately. Report zero training consumption.

Require fixture tests for future-response leakage, multi-call ambiguity, changed
option order, duplicate/conflicting teachers, schema violations and references,
cross-role server compositions, alias ownership and overlength inputs. Verify the
saved export from immutable source witnesses before marking it admitted. This
stage supplies breadth for supervised learning and does not replace the separate
retail outcome admission or live reinforcement-learning qualification.
